# Public attendance in attendee repositories

## Decision

The Public attendance audience means an explicit request to publish a standard `community.lexicon.calendar.rsvp` in the attendee's repository. The other six audiences remain local. Publication needs a configured existing calendar event URI/CID and an explicit attendee grant of `repo:community.lexicon.calendar.rsvp`. Normal sign-in remains identity-only. No generic transitional permission, event creation, automatic startup/login/read publication, migration, or scheduler is included.

Use the installed official OAuth SDK session fetch handler for authenticated record operations. Retain only explicitly scoped API sessions for a one-day storage TTL. Missing or revoked credentials need reauthorization. A single-process SDK lock hook and per-DID app mutation guard reject overlapping work instead of adding a queue. Recheck optimistic response versions after awaited remote reads before writes.

Persist one generated TID and the possible app-authored record values per attendee. Before updating or deleting, read that exact key, require matching app-authored content with exactly the three root keys and a non-null, non-array subject containing exactly `uri` and `cid`, and use `swapRecord` with the returned CID (or explicit null for creation). Never enumerate/adopt/delete other keys. A foreign modification requires manual resolution. `validate:false` allows a PDS that has not installed this community schema; the app constructs only the required subject strongRef and known status tokens. No schema is vendored.

Local visibility narrowing and deletion must not depend on PDS availability. Persist an uncertain remote state before network work, retain ownership after signup deletion, and distinguish confirmed publication/removal from uncertainty, authorization failure and content conflict. Persist `unresolvedPut` immediately before dispatching a put. An acknowledged put clears the flag only when there was no earlier unresolved put. A lost acknowledgement can leave a request still processing: the PDS may report absence during withdrawal and commit the earlier put later. Absence therefore cannot settle an unresolved put or clear any possible app-authored values. Explicit retry reads and reconciles the owned key, including deleting a matching late record. After an indeterminate put, retain the flag and possible values even after an acknowledged later deletion or put; report unconfirmed state rather than treating that one operation as proof that every earlier request has settled. This conservative state can persist indefinitely. No waiting-period guarantee, public tombstone, extra write, worker, or scheduler is introduced. There is no claim that deleting a record recalls external copies. No local transaction can atomically commit with a remote repository operation.

## Constraints

One event per instance, one Node process, one private SQLite database. Do not retarget an instance with existing published responses to another event. Restore database and key together. Removing local state cannot withdraw remote records. Public state is the last confirmed operation, not continuous monitoring of later edits made through another app. Refreshing credentials can extend their storage TTL; absent further user requests, purge expires them. A normal identity-only login may replace a prior scoped SDK session and require explicit reauthorization.

## Verification

Vitest uses real SQLite stores and mocked unmanaged SDK sessions. Route examples cover authorization/CSRF, forged fields, stale versions, concurrency, explicit-only publication, status mapping, narrowing, deletion, retry and ambiguous remote failure. A bounded seeded 24-operation edit/delete/read history compares remote presence with the local audience/attendance reference model (seed 17031, repeated public/update/clear/local-only/delete/recreate phases with varied local audiences); deterministic cases cover network failure/recovery and overlap. At baseline `aaf457f` plus this uncommitted change, the history failed against a deliberate missing-withdrawal defect in a disposable `.worktrees/rsvp-calibration` copy (`npm --prefix .worktrees/rsvp-calibration test -- src/server/app.test.ts -t 'matches local/private/public reference state'`); the copy was removed afterward. The generated supplement and calibration took roughly ten minutes and exposed no independent production defect beyond the ordinary SDK error-body regression covered separately. This is a small generated supplement, not a custom property-testing framework or proof of correctness. Two independently reviewed regressions were reproduced before fixes: an initial put timeout followed by an absent withdrawal read incorrectly reported removal and discarded ownership, and a foreign nested subject field was accepted for deletion. The deterministic HTTP/real-SQLite/SDK-mock history now checks timeout → absent withdrawal → late commit → explicit CAS deletion → another absent retry, retaining unconfirmed state and all possible values throughout. Subject-extra/null/array cases require a GET-only conflict. Both confirmed defects failed before and passed after the fixes. Live PDS authorization and record writes remain a consenting operator's prelaunch check.
